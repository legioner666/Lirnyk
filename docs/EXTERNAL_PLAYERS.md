# Керування зовнішніми плеєрами: офіційні шляхи

Документ підготовлено після P0 від 2026-11-26. Тоді Google Play Protect заблокував встановлення v0.1.1.

## Чому прибрано слухач сповіщень

Google прямо пише, що застосунки із «інтернет-джерел» блокуються під час встановлення, якщо оголошують `RECEIVE_SMS`, `READ_SMS`, `BIND_NOTIFICATION_LISTENER_SERVICE` або `BIND_ACCESSIBILITY_SERVICE`. Мова про застосунки, завантажені браузером, месенджером чи файловим менеджером ([Play Protect: guidance for developers](https://developers.google.com/android/play-protect/warning-dev-guidance)).

APK з GitHub — саме такий випадок. Тому з v0.1.2 у Lirnyk немає `NotificationListenerService`. CI зупиняє збірку, якщо слухач з'являється у фінальному маніфесті.

Без слухача сторонній застосунок не може отримати список активних медіасесій через `MediaSessionManager.getActiveSessions`. Цей метод доступний лише системним застосункам з `MEDIA_CONTENT_CONTROL` або застосунку з увімкненим слухачем сповіщень.

## Що лишається офіційним і без чутливих дозволів

| Шлях | Що дає | Обмеження |
|---|---|---|
| **Медіапідключення до самого плеєра**: `MediaController` / `MediaBrowser` (Media3) до його `MediaSessionService`, `MediaLibraryService` чи `MediaBrowserService` ([Android: connect to a media app](https://developer.android.com/media/media3/session/connect-to-media-app)) | Назва треку, стан, кнопки, які дозволяє плеєр; іноді перегляд бібліотеки | Плеєр сам вирішує, чи прийняти підключення від Lirnyk. Великі сервіси часто приймають лише відомі їм застосунки. Потрібен `<queries>` у маніфесті (з Android 11) — без чутливих дозволів |
| **Медіакнопки** через `AudioManager.dispatchMediaKeyEvent` | Грати, пауза, далі, назад — для плеєра, що грав останнім. Так само, як кнопки керма | Назви треку не видно. Не можна вибрати конкретний плеєр |
| **Відкрити плеєр** (intent запуску) | Швидкий перехід у Spotify, YouTube Music тощо | Керування — вже в самому плеєрі |
| Не використовуємо | `AccessibilityService`, приховані API, `MEDIA_CONTENT_CONTROL` (лише для системних застосунків), читання сповіщень | — |

## Що вже зроблено у v0.1.2

- «Перевірка магнітоли» показує, які встановлені застосунки надають публічне медіапідключення. Для цього використовується `<queries>` з трьома конкретними intent-діями, без `QUERY_ALL_PACKAGES`.
- Підключення до них ще не робиться: це Етап 2. Звіт з магнітоли покаже, з чим реально є сенс працювати.

## Пропозиція для Етапу 2 (на рішення власника)

1. Кнопки «Грати/Пауза/Далі/Назад» для «останнього плеєра» через `dispatchMediaKeyEvent`. Це працює для будь-якого плеєра і не потребує дозволів, але без назви треку.
2. Для плеєрів зі звіту — спроба `MediaBrowser`-підключення.
   - Якщо плеєр його приймає, показуємо назву і стан.
   - Якщо ні, чесно пишемо «лише кнопки».
3. Spotify відкладено, доки не вирішено спосіб поширення застосунку: GitHub чи Google Play.

## Інші причини попереджень Play Protect, які ми перевірили

| Причина з документації | Стан Lirnyk |
|---|---|
| Чутливі дозволи (SMS, слухач сповіщень, accessibility) | прибрано; CI перевіряє фінальний маніфест за списком дозволених дозволів |
| `targetSdkVersion` надто низький | target 36 |
| Невідомий застосунок → «надіслати на перевірку» | можливе для будь-якого нового APK; на встановлення не впливає, користувач може погодитись на перевірку |
| `isAccessibilityTool` | не використовується; CI перевіряє |
